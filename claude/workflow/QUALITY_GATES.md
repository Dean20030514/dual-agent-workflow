# 设计层闸门（UX / UI / 美术内容 / 文案）

> 门控：0.1 第 4/5/6/15 维；无界面或面向用户内容则整组跳过（**§5 清单唯一定义处**，`/design-check` 与 Reviewer 都读本节）。
> 三道复核：Phase 0/规划期先勾（预判，未想清算 Open Question）→ 实现完成自检 → Reviewer 复核（受 Reviewer-Lightweight Protocol 约束）。
> 产物化：需渲染才能判定的项，证据须为截图——**Critical**：命名 `docs/ai/screenshots/<task>-<断点>.png`，HANDOFF 指向；**Routine**：在对话里贴出截图即可（无 HANDOFF，也不得为此创建）。两模式一样的是**无截图不得勾过**。响应式/多主题分别覆盖项目声明的最小/最大断点与各主题，不支持则该项 N/A。

## 5.1 交互设计 UX
* [ ] 核心任务流顺畅：一眼看出"下一步做什么"，主路径不被次要操作打断。
* [ ] 步骤最少化：点击/输入压到合理最小，无冗余确认/跳转。
* [ ] 状态全覆盖：加载/空/错误/成功/边界（超长、零数据、极值）逐一设计。
* [ ] 反馈清晰即时：每个动作有可感知反馈，无"点了没反应"。
* [ ] 错误可恢复：告诉用户"发生了什么+怎么办"，不裸露堆栈；破坏性操作有确认/撤销。
* [ ] 符合平台习惯：导航/手势/快捷键/返回遵循目标平台约定。
* [ ] 键盘可达等可访问性见 11.4。

## 5.2 视觉设计 UI
* [ ] 层级清晰：尺寸/字重/对比建立优先级，主次一眼可辨。
* [ ] 专业可信：观感像真实产品截图，不像半成品。
* [ ] 成体系：颜色/字体/间距/圆角/阴影来自设计系统或集中 token。
* [ ] 避免廉价模板感：不直接套库默认外观，有明确风格方向。
* [ ] 多主题/响应式：若支持，每主题与断点单独验收（截图为证）。
* [ ] 前端细则遵循项目/全局规范；对比度阈值见 11.4。

## 5.3 美术 / 内容表现
* [ ] 有审美与记忆点：视觉有可识别特征。
* [ ] 情绪基调一致：色彩/构图/动效/音画与品牌调性一致（品牌调性见 PRODUCT_BRIEF，由 /define 0.4 产出）。
* [ ] 素材规格合理：尺寸/格式/压缩/命名符合约定；Web 素材守性能预算。
* [ ] 跨密度/跨分辨率适配：高 DPI/多分辨率不模糊不变形。
* [ ] 动效服务理解而非装饰；reduced-motion 见 11.4。

## 5.4 内容 / 文案
* [ ] 信息架构清楚：分组与命名让用户快速定位，标题层级对应视觉层级。
* [ ] 文案准确不夸大：与实际功能一致，不把假设写成事实。
* [ ] 空状态/错误文案齐备：空列表/加载失败/权限不足/校验失败都有人话提示。
* [ ] 语气一致：称谓/标点/术语遵循内容规范。
* [ ] 多语言需求已判定：需要则技术细则见 11.4，不需要就地 N/A + 原因。

## 11.1 测试 / QA（触发：改动可执行代码；纯文档/注释 N/A）
* [ ] 单元/集成/E2E 覆盖关键路径（happy path 至少一条端到端）。
* [ ] 边界与异常：空值/越界/超长/并发/超时/外部依赖失败各有针对性用例。
* [ ] 覆盖率：有门槛则遵守；无工具则确保关键路径与回归覆盖，不凑百分比、不编造数字。
* [ ] 涉及历史 bug/既有行为时有回归用例锁定；声称「回归用例有效」时须有守护证据——**判据两模式恒适用，证据形式按模式取**（Critical = 装置的结构化产物；Routine = 在对话里把同一套六步协议跑完并逐步展示，**判据一条不减**，只是不创建 Critical 产物）。**两种形式的具体要求以 `AGENTS.md` → 守护有效性装置 ★ 模式分流为准，本清单不局部枚举**——缩写成「一条负向命令 + 输出」就是把完整守护降成单次运行，等同空守护。
* [ ] 测试真实运行、证据可独立复核——**Critical**：产物化到 `last_test_run.txt`；**Routine**：对话内展示真实命令 + 完整输出 + 退出码（无该文件，也不为此创建）。

## 11.2 安全（核对项，非禁止事项；红线唯一出处 AGENTS.md）
**基础安全（恒查·所有代码任务·不可整组 N/A；纯文档退化为"无新增密钥/链接/凭据"一条）：**
* [ ] 无硬编码密钥/token/密码/连接串（走环境变量/密钥管理）。
* [ ] 所有系统边界输入做校验（用户输入/API 响应/文件内容/外部数据一律不可信）。
* [ ] 错误信息与日志不泄露敏感数据（堆栈/内部路径/密钥/PII 不外抛）。
* [ ] 依赖与锁文件：新增/升级有来源、锁文件改动与依赖一致、无可疑传递依赖。

**敏感面扩展（触发：认证/授权/支付/用户数据/外部输入/文件上传/对外网络服务；不涉及标 N/A + 原因）：**
* [ ] authn/authz 到位，无越权、无认证绕过。
* [ ] 常见漏洞面排查：注入(SQL/命令/模板)/XSS/CSRF/SSRF/路径穿越/反序列化/开放重定向（按栈取适用项）。
* [ ] CORS/session cookie/CSRF token 配置正确；上传文件做类型与大小校验。
* [ ] 速率限制/防滥用/资源耗尽防护（对外接口）。
* [ ] 密钥/凭据有最小权限与轮换路径；敏感操作有审计。
* [ ] 必须执行 security review：环境支持则派 security-reviewer sub-agent，否则 Author 按本组逐项核对（强制，非可选）。

## 11.3 隐私 / 合规（触发：处理用户数据/PII/行为日志/可识别标识；纯内部无用户数据标 N/A + 原因）
* [ ] 已识别是否处理 PII（姓名/邮箱/手机/位置/设备 ID/生物特征），列出哪些字段。
* [ ] 数据最小化：只采集/存储/传输真正需要的字段，无"先存着以后可能用"。
* [ ] 留存与删除：有明确留存期与删除路径（含用户行使删除权的级联清理）。
* [ ] 同意与告知：采集前有告知/同意机制（按场景取适用项）。
* [ ] 已判断是否触及数据保护法规（按数据类型+地域），结果与依据写入 PRODUCT_BRIEF；若触及或不确定，在 HANDOFF/待验证清单登记并标 needs-human-legal，**未自行下合规结论**。
* [ ] 第三方处理方/数据共享：是否把用户数据传给第三方（分析/云/模型 API）已识别记录；跨境传输标 needs-human-legal。
* [ ] 训练数据/模型日志用途：用户数据是否进训练或被日志留存，已明确并在采集时告知。
* [ ] 日志/监控/错误上报/分析事件中不打印 PII。
* [ ] 涉及用户/数据的判断区分证据/假设（规则见 AGENTS.md）。

## 11.4 可访问性 / 普适性（触发：有界面或面向最终用户内容；纯后端/库标 N/A + 原因）
* [ ] 键盘可达：所有交互可仅用键盘完成，焦点可见、tab 顺序合理、无焦点陷阱（CLI：无强制鼠标/图形依赖）。
* [ ] 对比度：文字与背景达标（默认 WCAG AA；项目另有规定从项目）。
* [ ] 语义结构/替代文本：语义标签、标题层级、图像 alt、表单 label、ARIA 用对非滥用。
* [ ] 尊重 reduced-motion：用户偏好减少动效时禁用/弱化非必要动画。
* [ ] 国际化与本地化：文案可翻译、无写死拼接、日期/数字/货币按 locale、支持 RTL（如适用）。
* [ ] 低端设备/弱网兼容：弱网有降级与加载态、低端设备不卡死、包体在预算内。

# 上线后：数据分析 / 运营增长 / 客服与用户成功

> 门控：0.1 第 11/12/16 维；仅当交付真实可发布、有真实用户的产品（或其上线改动）时展开。关于用户行为/渠道/留存的判断同样区分证据/假设（规则见 AGENTS.md）。

## 12.1 数据分析
* [ ] 北极星与支撑指标按 PRODUCT_BRIEF（/define 0.5 定义）的口径追踪（本组不重定义，只追踪与口径核对）。
* [ ] 关键埋点已在代码中实现并验证可触发（在 last_test_run.txt 或手动验证产物中证明，非仅文档声明）。
* [ ] 避免虚荣指标：PV/下载/累计注册等不进决策面板；每个指标要能答"它变了我会改什么动作"。
* [ ] 数据不作恶：只采必需字段、可匿名化、对用户透明（隐私见 11.3）；埋点不偷采计划外数据。
* [ ] 口径可信：核心指标有口径文档，避免同一指标多处口径打架。

## 12.2 运营增长（AARRR 或等价，每环一两行）

| 环节 | 口径/关键事件 | 证据 vs 假设 |
|------|--------------|-------------|
| Acquisition | 主要渠道/如何衡量到站 | |
| Activation | "第一次获得价值"定义 + 埋点 | |
| Retention | 留存口径(次日/7日/月活) + 基线→目标 | |
| Referral | 是否有分享/邀请回路(无则 N/A) | |
| Revenue | 本阶段是否考虑(归 0.4) | |

* [ ] 任何"做这个能涨留存/转化"的判断标证据 vs 假设；假设进待验证清单，最小实验验证后再放大。

## 12.3 客服与用户成功
* [ ] 反馈回路：用户从哪反馈 → 谁先看到 → 多久响应。
* [ ] 责任人已指派：上线后谁接用户问题，不能无人认领。
* [ ] 常见问题沉淀路径：高频问题回流产品或文档/FAQ；反复出现的登记到 backlog/Known Issues 或 PRODUCT_BRIEF 的 Recurring Support Issues；仅当根因落在具体文件/模块、可指定 Payback trigger 时才用 [DEBT] 明账。
* [ ] 闭环验证：挑一条最近反馈，能说出它进了哪个 backlog 项。

## 12.4 上线与可运维性（真实产品）
* [ ] 上线验证：发布后有冒烟/健康检查确认核心路径可用。
* [ ] 回滚路径：明确如何快速回滚（版本/开关/数据迁移可逆性）。
* [ ] 监控与告警：核心指标/错误率有监控，异常有告警通道。
* [ ] 事故归属：incident owner 已指定。

# 组织与角色分配（轻量）

> 只做"本任务派给谁"的一次性分工记录。落点：HANDOFF 的 Next Step 附近一两行，或 PLAN 的 Execution Steps 标注负责角色。

本任务派给哪些 sub-agent / 角色（按需勾选）：

> **环境不提供对应 sub-agent 时，该角色职责由 Author 本人承担并在 HANDOFF 注明 —— 只降级执行方式，不降级职责。**（本机现状：这批专家 agent 曾由 `ecc` 插件提供，该插件已于 2026-07-25 **卸载**，故本机一个专家 agent 都没有 —— 降级路径见 `~/.claude/rules/common/agents.md`）

* [ ] **planner** — 复杂功能/重构，先出实现计划。
* [ ] **architect** — 涉及架构决策/跨模块边界。
* [ ] **tdd-guide** — 新功能/bug 修复，测试先行。
* [ ] **code-reviewer** — 写完代码后通用质量审查。
* [ ] **security review** — 触碰 auth/支付/用户数据/外部输入时强制（见 11.2）。
* [ ] **language-specific reviewer**（[python-reviewer / rust-reviewer / ...]）— 按栈选。
* [ ] **doc-updater / refactor-cleaner / e2e-runner** — 按任务性质选。

> 并行优先：相互独立的审查/分析用并行 Task 派发。派 sub-agent 时要求继承主对话模型不降级（成本理由见 `~/.claude/workflow/workflow-design-notes.md`）。

人类负责（不可代劳）：
* [ ] 批准产品定义(Phase 0)与实现计划；PLAN 的 Human Approval Status 是唯一受保护字段，只能人类改。
* [ ] 检查 diff、决定取舍、对模糊需求与设计争议拍板。
* [ ] 最终 commit/squash；确认后才清理 Reviewer scratch 目录。

项目管理（第 17 维，轻量）：默认由开发主干隐式覆盖；跨多人/多里程碑时显式过：
* [ ] 任务已拆到可独立验收的步骤，落入 PLAN 的 Execution Steps。
* [ ] 依赖/阻塞已识别并写明。
* [ ] 交付节奏/里程碑记入 HANDOFF 的 Next Step。
