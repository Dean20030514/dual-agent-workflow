# A/B 模型诊断：同任务 4.8 vs 5（判「能力回退」vs「上下文锚定」）

> 何时用：怀疑某模型在"严格按约束做小型修复"这类任务上退化/波动（如 Opus 5 的局部修 + 滚补丁 + 停止条件失效）。判因用，跑一次即可；日常防护靠 `/debug` 回归安全修复协议（杠杆 A/B/C），不靠本实验。

## 设置（严格控制变量）
1. **同一干净提交**：两次都从同一个 clean commit / clean base diff 起，不带任何前序补丁。
2. **各自全新上下文**：两个模型各开一个**全新会话**，互不可见对方的修复/复盘/推理。
3. **完全相同的输入**：同一 `TASK_BRIEF`（需求 + 验收条件逐字一致）、同一工具权限、同一 Reviewer（同一 Codex prompt / 同 9A+9B）。
4. **同一评审标准**：Reviewer 按同标准给 blocking，两边一致。

## 逐轮记的指标
| 指标 | 说明 |
|---|---|
| 首轮 blocking 数 | 第一次 review 报了几个 |
| **每轮新增 blocking** | 每轮 fix 后 Reviewer 新报几个（**"修 A 破 B" 的直接度量**）|
| 补丁规模 | 每轮 diff 行数 / 触及文件数（抽象冲动/大补丁的度量）|
| 是否产债 | 有无 `[DEBT]` / 绕过 validation-auth / 删测试 |
| 收敛轮数 | 到"零 blocking"用了几轮（不收敛也记）|

## 判读

> **下列结论只用于判因，不直接授权任何恢复动作。** 何时停手、能否回退、能否换上下文或换模型，一律按 `AGENTS.md` → 停止事件优先级 判：失败两次先停手报告人类，只有人类随后明确要求回退重启，才进入 `/debug` 的 fresh-context 分支。
- **5 在全新上下文里仍明显更差**（新增 blocking 多、补丁大、不收敛）→ **该类任务能力侧重回退** → 可考虑 review-fix 阶段改用 4.8；杠杆 A/B/C 照样降风险。
- **5 全新上下文正常、只有长对话里差** → 主因是**上下文锚定/路径依赖** → **杠杆 B（卡住换新上下文）最关键**：日常修复到 2 次失败就换 fresh sub-agent。
- **两者同时成立**（原始诊断的倾向）→ 两手都上：A/C 常态强制 + B 恢复机制 + 必要时 fix 阶段换模型。

> 隔离纪律：**绝不让两个模型看到对方的修复或复盘**（会污染 fresh-context 对照，把实验做废）。
