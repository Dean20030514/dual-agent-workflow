# Phase 0：产品定义 / 需求澄清（门控入口）

先读 `AGENTS.md` 并遵守其 Safety Rules（项目无 AGENTS.md 则从 `~/.claude/workflow/AGENTS.md` 母本 scaffold）。

本次任务：$ARGUMENTS

不写代码，只答两件事：**值不值得做、做成什么样算对**，并决定 18 维哪些展开。
时序：只读判断可在建分支前；任何文件落盘（PRODUCT_BRIEF / TASK_BRIEF）在 `git checkout -b` 之后。
落点：产品级长期结论 → `docs/ai/PRODUCT_BRIEF.md`；本次适用性扫描 + 用户故事/验收 → `docs/ai/TASK_BRIEF.md`。0.1~0.5 是草稿，只落结论不照抄过程表。

**「真实可发布产品」判据**（决定产品/上线层是否触发）：① 会被本团队外的真实用户使用；② 有独立发布/上线动作。满足 ① 或 ② 即触发产品/上线层（0.4、0.5、上线后清单）。③「会长期维护」不单独触发商业/品牌/增长层，只加强工程质量与债务纪律。① ② 皆否 = 内部/一次性任务，产品/上线层默认 N/A。
注意：设计层闸门（`/design-check`）不受本判据控制，只由 0.1 第 4/5/6/15 维触发——有界面或面向用户内容就要过。

## 0.2 产品定位 + 用户研究

**定位**（一段话答三件事）：① 解决谁的什么具体痛点；② 为什么是现在；③ 对照 1~2 个现有替代品（含"手工干"），凭什么更好。

**用户研究**：每条用户/市场判断必须按 `AGENTS.md` 的「证据 vs 假设标签」规则标注。所有 `[假设]` 进下表：

| 假设 | 影响什么决策 | 唯一依据? | 最低成本验证方式 | 状态 |
|------|------------|----------|----------------|------|
| [原文] | [若为假，哪个范围/优先级要改] | 是/否 | [5 人访谈/翻竞品评论/埋点/灰度] | 待验证 |

硬门：标「唯一依据=是」的高影响假设，进入实现前必须已验证转 `[证据]` 或显式降级（呼应 `/plan` 的 Unknown 即 blocking）。

## 0.3 产品策划：需求 → 可执行

产出直接喂给 TASK_BRIEF（Goal/Acceptance）与 IMPLEMENTATION_PLAN（Proposed Changes/Testing）。
* **用户故事**：`As a <role>, I want <capability>, so that <value>.`
* **可验证验收**：每条配 1~N 条 `Given/When/Then`，避免"好用/流畅"，能对应测试命令/可截图者优先。
* **优先级**：MoSCoW 或 P0/P1/P2，二选一全局一致。
* **范围边界**（强制）：显式列 In scope / Out of scope；模棱两可一律放 Out of scope。

> 验收条件单一事实源 = TASK_BRIEF 的 Acceptance Criteria；0.3 起草，正式规划时精炼进 TASK_BRIEF。

## 0.4 商业模式 + 品牌 + 内容策略（门控：0.1 第 13/14/15；N/A 整节跳过，各项一两行）

* **商业模式**：价值创造/传递/捕获；谁付费；成本结构（单位成本会否随规模失控）。
* **品牌**：一句话定位；调性；核心记忆点 + 信任锚。
* **内容策略**：是否在卖内容；内容从哪来（自产/UGC/授权/模型生成）；由谁维护（无人维护=不存在）。

## 0.5 成功度量预定义（门控：0.1 第 11；内部/一次性可只写"成功=验收全过"+N/A）

* **北极星（唯一）**：最能代表用户获得核心价值的单一可度量指标，不是营收/注册量。
* **支撑指标（1~3）**：留存/转化/时延/错误率，每个写明采集方式 + `event name + 触发时机 + 属性字段` schema。
* **基线与目标**（推荐）：当前值 → 期望值；无基线则本次先建基线。
* **上线后谁接用户**：反馈走哪条通道。无人接 = 不算可发布。
