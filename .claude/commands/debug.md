# 系统化调试

不允许"试着改改看"。与全局"同一修复连续两次失败即停下报告"硬规则衔接。

**铁律：没定位根因前，不许动手改。**「先试着改 X 看会不会好」是头号反模式。

四阶段按序走：

1. **根因调查**：逐字读 error + stack trace（含行号）；能否稳定复现？最近改了什么？多组件系统在每层边界加诊断 log（打印入参/出参/关键状态），先确定"哪层断的"；沿数据流向上追坏值从哪来，追到源头，不在症状处堵。
2. **模式对照**：找一处能正常工作的相似代码，完整读（不跳读），逐条列出 working 与 broken 的每个差异——根因常在差异里。
3. **假设与验证**：写下"我认为根因是 X，因为 Y"；一次只改一个变量验证；没中就换假设，不堆多个 fix。
4. **实现修复**：先写能复现该 bug 的失败用例 → 只针对根因改最小一处 → 跑验证（回归红→绿）。

**反复尝试仍失败 → 停手**：第二次失败就停，回阶段 1 重做根因调查，不继续堆 fix；若根因指向"问题在底层设计/假设"，判为架构问题、上报人类。

**红旗（出现即代表偏离根因调查，借口 → 现实）**：

| 借口 | 现实 |
|---|---|
| "先快速修一下，回头再查" | 没根因的修复只是把 bug 移位，回头不会来 |
| "改一下 X 试试能不能好" | 这是猜不是调试；先定位再改 |
| "多改几处一起跑测试看" | 一次只改一个变量，否则分不清谁起作用 |
| "应该是 X 的问题，我修 X"（没验证） | 未验证的假设不是根因 |
| "再试最后一次"（已试 2 次以上） | 回阶段 1，别堆 fix |

> 调试期任何改动同样受声称完成纪律（见 `/implement`）约束：说"修好了"前复现用例必须真的红→绿。
